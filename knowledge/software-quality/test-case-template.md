# 测试用例标准模板

---

## 一、单条用例必备 9 要素

每条测试用例必须包含以下全部要素：

| # | 要素 | 说明 | 反例（禁止） |
|---|------|------|-------------|
| 1 | **用例编号** | `TC-<模块缩写>-<序号>`，如 `TC-AUTH-001` | 无编号 |
| 2 | **所属模块/功能点** | 关联到需求 Feature ID，如 `F01: 用户登录` | 不写归属 |
| 3 | **优先级** | P0 核心 / P1 重要 / P2 一般 / P3 锦上添花 | 不分级 |
| 4 | **前置条件** | 数据、状态、权限、环境准备 | "系统正常" |
| 5 | **测试数据** | 具体的输入值 | "输入合法数据" |
| 6 | **操作步骤** | 明确、可复现、有序号 | "测试登录功能" |
| 7 | **预期结果** | 可验证、具体到数据/提示/状态变化 | "功能正常" |
| 8 | **用例类型** | 正向/反向/异常/边界/兼容/性能/安全 | 不标注类型 |
| 9 | **关联需求** | 可追溯到需求 ID | 不关联 |

---

## 二、用例文档格式（Markdown）

```markdown
### TC-AUTH-001: 正确用户名密码登录成功
- **功能点**: F01 用户登录
- **类型**: 正向
- **优先级**: P0
- **前置条件**: 已注册用户 testuser，密码 Test@1234，账号状态正常
- **测试数据**:
  - 用户名: `testuser`
  - 密码: `Test@1234`
- **步骤**:
  1. POST `/api/auth/login` body: `{"username": "testuser", "password": "Test@1234"}`
  2. 检查响应
- **预期结果**:
  - HTTP 200
  - 响应体包含 `token` 字段（非空 JWT）
  - 响应体包含 `user.username = "testuser"`
- **关联需求**: REQ-AUTH-001
```

```markdown
### TC-AUTH-002: 密码错误登录失败
- **功能点**: F01 用户登录
- **类型**: 反向
- **优先级**: P0
- **前置条件**: 已注册用户 testuser，正确密码 Test@1234
- **测试数据**:
  - 用户名: `testuser`
  - 密码: `WrongPass123`
- **步骤**:
  1. POST `/api/auth/login` body: `{"username": "testuser", "password": "WrongPass123"}`
  2. 检查响应
- **预期结果**:
  - HTTP 401
  - 响应体包含错误提示（非技术堆栈）
  - 不返回 token
- **关联需求**: REQ-AUTH-001
```

## 三、结构化用例格式（JSON，供自动化消费）

```json
{
  "id": "TC-AUTH-001",
  "name": "正确用户名密码登录成功",
  "feature": "F01",
  "type": "positive",
  "priority": "P0",
  "preconditions": [
    "已注册用户 testuser，密码 Test@1234，账号状态正常"
  ],
  "test_data": {
    "username": "testuser",
    "password": "Test@1234"
  },
  "steps": [
    "POST /api/auth/login body: {\"username\": \"testuser\", \"password\": \"Test@1234\"}"
  ],
  "expected": [
    "HTTP 200",
    "响应体包含 token 字段（非空 JWT）",
    "user.username = testuser"
  ],
  "automation_command": "curl -s -X POST https://$BASE_URL/api/auth/login -H 'Content-Type: application/json' -d '{\"username\":\"testuser\",\"password\":\"Test@1234\"}' -w '\\n%{http_code}'",
  "requirement": "REQ-AUTH-001"
}
```

## 四、喂给 LLM 的提示模板

当需要 LLM 为一个功能模块生成测试用例时，使用此模板：

```
角色：你是资深测试专家。
任务：基于以下【需求规格】和【功能清单】，设计全面的测试用例。

【需求规格】
<粘贴需求文档 / PRD / 接口文档>

【功能清单】
<粘贴本功能涉及的功能点列表>

要求：
1. 先用「场景法」梳理出基本流、备选流、异常流；
2. 再对每个功能点，按以下覆盖维度逐项设计用例，每个维度至少给出对应用例，
   不适用的维度需显式说明"不适用及原因"：
   输入(等价类/边界值/格式/特殊字符) / 处理逻辑 / 输出 / 增删改查闭环 /
   状态流转 / 异常与超时 / 并发 / 权限与越权 / 兼容性；
3. 非功能方面，按以下维度判断是否需要测试并给出要点：
   性能、安全(注入/越权/敏感信息)、可靠性(容错/恢复)、兼容性、易用性、安装升级；
4. 每条用例必须包含：编号、模块、优先级、前置条件、测试数据(具体值)、
   操作步骤、预期结果(具体可验证)、用例类型、关联需求；
5. 用 Markdown 表格输出；
6. 完成后做一次自检：列出"可能仍有遗漏的场景"清单。
```

### 使用技巧

- 一次只投喂一个模块，比一次全量投喂质量更高
- 让 LLM 先输出"测试点清单"，确认无遗漏后再展开成用例
- 用非功能 checklist 作为评审 checklist，反向检查产出的用例是否漏维度
- 对 API 接口，务必让 LLM 给出可直接执行的 curl/httpie 命令
