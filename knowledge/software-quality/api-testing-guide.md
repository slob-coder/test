# REST API 测试指南

> 适用于 REST/HTTP API 的系统测试。
> 覆盖输入校验、状态码、错误处理、认证、并发等维度。

---

## 1. HTTP 方法语义验证

| 方法 | 幂等 | 测试重点 |
|------|:---:|---------|
| GET | ✅ | 不应修改数据；重复调用结果一致 |
| POST | ❌ | 重复提交是否产生重复数据 |
| PUT | ✅ | 完整替换 vs 部分更新的行为 |
| PATCH | ❌ | 部分更新是否只改指定字段 |
| DELETE | ✅ | 删除不存在的资源返回 404 还是 204 |

**测试点**：
- 用错误的 HTTP 方法访问（GET 接口用 POST 调）→ 应返回 405
- HEAD 请求是否返回和 GET 相同的 Header
- OPTIONS 请求返回的 Allow 头是否正确

---

## 2. 状态码覆盖

每个接口至少覆盖以下状态码场景：

| 状态码 | 场景 | 必须覆盖 |
|--------|------|:--------:|
| 200 | 成功（GET/PUT/PATCH） | ✅ |
| 201 | 创建成功（POST） | ✅ |
| 204 | 成功但无内容（DELETE） | ✅ |
| 400 | 请求体格式错误/校验失败 | ✅ |
| 401 | 未认证（无 Token / Token 过期） | ✅ |
| 403 | 无权限（Token 有效但权限不足） | ✅ |
| 404 | 资源不存在 | ✅ |
| 405 | 方法不允许 | ⚪ |
| 409 | 冲突（重复创建/并发修改） | ⚪ |
| 413 | 请求体过大 | ⚪ |
| 422 | 语义错误（格式对但业务不合法） | ⚪ |
| 429 | 频率限制 | ⚪ |
| 500 | 服务端内部错误（不应正常触发） | ✅ |

## 3. 输入校验 Checklist

对接口的每个参数逐项检查：

### 路径参数
- [ ] 不存在的 ID → 404
- [ ] 格式错误的 ID（字母代替数字）→ 400
- [ ] 他人的 ID（越权）→ 403
- [ ] 空路径段 `/api/users//profile` → 400 或 404

### 查询参数
- [ ] 缺少必填参数 → 400 + 明确提示
- [ ] 参数类型错误（page=abc）→ 400
- [ ] 参数超出范围（page=-1, limit=10000）→ 400 或截断
- [ ] 多余参数是否被忽略
- [ ] 重复参数（?a=1&a=2）的处理

### 请求体
- [ ] 空 body → 400
- [ ] 缺少必填字段 → 400 + 明确指出缺哪个字段
- [ ] 字段类型错误（数字字段传字符串）→ 400
- [ ] 额外字段是否被忽略（不应存入数据库）
- [ ] 嵌套对象中的校验是否生效
- [ ] Content-Type 不匹配（如 form 接口传 JSON）→ 415 或 400

### 请求头
- [ ] Authorization 头缺失 → 401
- [ ] Authorization 头格式错误（不带 Bearer 前缀）→ 401
- [ ] Content-Type 缺失或错误
- [ ] Accept 头不支持的类型

---

## 4. 分页与列表

- [ ] 不传分页参数 → 使用默认值（记录默认值是多少）
- [ ] page=0 vs page=1（哪个是第一页）
- [ ] page 超出总页数 → 返回空列表 + 正确的 total
- [ ] limit=0 → 返回空或报错
- [ ] limit 超大值（limit=999999）→ 截断到最大值
- [ ] 排序参数：合法字段、非法字段、SQL 注入 payload
- [ ] 筛选/搜索：空值、特殊字符、SQL 注入 payload
- [ ] 空数据集：列表为空时的响应格式是否正确

## 5. CRUD 闭环验证

对每个资源进行完整闭环：

```
1. POST 创建 → 记录返回的 ID
2. GET 查询 → 验证数据与创建时一致
3. PUT/PATCH 修改 → 验证只修改了指定字段
4. GET 再次查询 → 验证修改生效
5. DELETE 删除 → 验证返回 204/200
6. GET 再次查询 → 验证返回 404
7. 检查关联数据 → 级联删除或引用保持
```

---

## 6. 并发安全

- [ ] 并发创建同名资源 → 是否有唯一约束保护
- [ ] 并发修改同一资源 → 最终数据是否一致（乐观锁 / ETag）
- [ ] 并发删除 + 修改同一资源 → 不应 500
- [ ] 高频调用 → 限流是否生效

**curl 并发测试模板**：
```bash
# 10 个并发请求
for i in $(seq 1 10); do
  curl -s -X POST "$BASE_URL/api/resource" \
    -H "Authorization: Bearer $TOKEN" \
    -H "Content-Type: application/json" \
    -d '{"name": "test"}' &
done
wait
```

## 7. 错误响应格式一致性

所有错误响应应遵循统一格式：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "用户名不能为空",
    "details": [
      {"field": "username", "reason": "required"}
    ]
  }
}
```

**检查点**：
- [ ] 所有 4xx/5xx 响应是否遵循统一格式
- [ ] 错误消息是否对用户友好（不暴露内部实现）
- [ ] 错误码是否有文档化的枚举
- [ ] 500 错误是否隐藏了堆栈信息
